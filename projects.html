Built to Grow: My Portfolio System

The Brief

I needed a single site to hold every project and case study I produce going forward — one that could grow term over term without a rebuild each time.

The Build

I split the site into independent pages (home, about, projects, contact) rather than one long scroll. Each project doubles as its own case study, opening in this slide-in panel so the grid stays a fast visual scan while the full write-up is one click away.

The Trade-off

I chose plain HTML/CSS over a framework or static site generator. That kept the build simple and dependency-free while I was still learning fundamentals, at the cost of manually duplicating markup (e.g. the header/footer on every page) instead of templating it.

The Result

The structure has held up across three terms of new content without needing a rewrite. The next improvement is reducing that markup duplication — likely by moving to a build tool or JS-rendered includes for shared header/footer.

From Catalog to Cart: Urban Threads

The Brief

Every project before this one either had no backend at all or leaned on localStorage. This assignment needed real accounts and a cart that actually persists — Firebase Authentication and user-specific state, not hardcoded product data.

The Build

Products load dynamically on the shop page, while each signed-in user's cart is kept separate from the public catalog rather than relying only on localStorage.

The Trade-off

I let shoppers browse and search the whole catalog without an account, and only prompt for login at the moment they click "Add to Cart." That's more work than just gating the entire shop behind a login wall, but it matches how real stores behave — you don't need an account to window-shop.

The Result

Fully working store with category filtering, search, and pagination on top of the base requirement. Next step is an admin panel so I can manage the product catalog from a form instead of typing documents into the Firebase console by hand.

Notes, Labels & State: Google Keep Rebuilt

The Brief

I'd already built this as a vanilla JS clone. The React version had to prove I could actually structure an app with components and shared state instead of one long script — plus add one manual feature and one AI-assisted feature and be honest about which was which.

The Build

Every piece of state — notes, labels, theme, reminders — lives in one hook, useKeepStore, instead of scattered across components. Labels were the manual build; dark mode and drag-and-drop reordering were the AI-assisted features, where I used AI to help scaffold the logic and then verified every interaction by hand in the browser.

The Trade-off

Notes still persist to localStorage rather than a backend. That kept the assignment focused on component structure and state management rather than infrastructure, at the cost of notes not syncing between devices the way Urban Threads' cart does.

The Result

Masonry note grid, label filtering, archive/trash with a 7-day auto-purge, and reminders with due-date sorting all work. Next step is swapping localStorage for Firebase, the same pattern I already proved out on Urban Threads.

From Query to Cover: Book Library

The Brief

Every project so far used data I controlled — hardcoded or localStorage. This one needed a real third-party API, which meant handling failures and slow responses instead of assuming the data is always just there.

The Build

Book data comes from the Open Library API via fetch, with explicit loading and error states rather than a blank screen while the request is in flight or on failure. Search is submit-triggered rather than live-as-you-type, to avoid firing a request on every keystroke.

The Trade-off

Submit-triggered search costs a bit of the instant feedback a live search gives you, but it keeps request volume sane against a free public API with no key or rate-limit budget behind it.

The Result

Deployed to GitHub Pages — including tracking down a blank-page bug that turned out to be a missing base: './' in vite.config.js. Next step is adding pagination to the search results, the same way I added it to Urban Threads' product grid.

Making Every Answer Count: Quiz Widget

The Brief

I wanted a small project focused purely on JavaScript logic — tracking a score and a question index correctly — rather than layout, which every earlier project had already covered.

The Build

Score and question index are tracked in JavaScript variables, not read back from the DOM, so the result is always computed rather than counted off whatever happens to be on screen. Answer buttons use event delegation on the container instead of a separate listener per button.

The Trade-off

Questions are hardcoded directly in the JS file rather than loaded from a separate JSON file or API. For a quiz this size that's the right call — pulling in a fetch layer for a dozen static questions would be complexity with no real payoff.

The Result

Instant feedback per question and a final score screen at the end. Next step is moving the question set into its own JSON file so I can add more questions without touching the scoring logic at all.

A Feed That Remembers: Twitter/X Clone

The Brief

Every project before this one was a static layout clone — good for CSS practice, but none of them needed to remember anything. I wanted a build that had to track state and respond to user actions in real time, closer to how a real product behaves.

The Build

I rebuilt the core Twitter/X feed interface with HTML and CSS for the layout, then used JavaScript to handle interactions — composing a post, updating counts, and reflecting state changes in the DOM immediately rather than reloading anything.

The Trade-off

I kept state in memory in the browser rather than wiring up a backend or persistence layer. That let me focus on getting the interaction logic and DOM updates right first, at the cost of nothing being saved between page reloads.

The Result

It's my most functionally complete project so far — real interactivity rather than a static clone. The next step is adding persistence, likely with local storage first and an API later, so state survives a refresh.

Six Builders, One Ship: iHub Capstone

The Brief

Every project before this one was solo — one person, one repo, no coordination needed. This capstone put six people on the same codebase at once, which meant the real challenge wasn't just building the site, it was making sure six people's work could merge without constantly breaking each other's changes.

The Build

As Git Manager, I helped keep the team aligned through clear communication and a feature-branch workflow — everyone worked on their own branch, opened a pull request, and I reviewed it before it merged into main. That gave me a single checkpoint to catch conflicts and layout regressions before they landed, instead of finding out after the fact.

The Trade-off

Requiring review before every merge slowed us down compared to everyone pushing straight to main — but on a 6-person team touching the same pages, that checkpoint is what kept the site from breaking every other day. Slower and stable beat fast and broken for this team size.

The Result

Shipped a full multi-page site with zero unresolved merge conflicts reaching main. The role taught me more about Git itself — rebasing, resolving conflicts, protecting a branch — than any solo project had. Next step is applying the same branch-protection workflow to my own solo repos going forward.

Turning an Error Into an Experience: Animated 404

The Brief

Our group needed to replace a plain Page Not Found message with a responsive 404 experience that felt intentional, animated, and useful to visitors.

One Cart, Shared State: Online Mall

The Brief

Our group needed to build a responsive shopping experience with a live product catalog, filtering, pagination, a cart, and checkout behavior that felt like one connected application.

The Build

We used React Context providers to share product and cart state across the navigation, catalog, product cards, pagination, and checkout drawer. Products come from DummyJSON with a fallback list for failed requests, while pricing handles South African VAT, delivery, payment methods, and installment plans.

The Trade-off

Context kept the shared state understandable for this project and avoided adding Redux setup, but the growing application still depends on clear provider boundaries and disciplined component responsibilities.

The Result

A deployed, responsive online mall with catalog search, categories, pagination, theme persistence, cart calculations, and a multi-step checkout experience built as a group.

A Board That Remembers: PinBoard

The Brief

The project needed to go beyond a static note layout and support the everyday actions a note board needs: creating, editing, searching, archiving, restoring, and deleting notes.

The Build

I built the note board in vanilla HTML, CSS, and JavaScript, with a single state model rendered into the board and persisted to localStorage. The interface also includes color selection, tooltips, a responsive sidebar, and an undo window after deletion.

The Trade-off

Keeping the app fully static makes it simple to deploy and run without a backend, but localStorage means notes remain tied to the current browser instead of syncing across devices.

The Result

A live, responsive note-taking app that demonstrates practical state management, persistence, filtering, and interaction design without a framework or build step.

A Platform in Three Parts: Airbnb Clone

The Brief

The project needed more than a static landing page: it needed separate experiences for guests and hosts, plus an administration area for managing the platform.

The Build

I organized the repository into independent frontend, backend, and admin applications so each part of the product has a clear responsibility and can evolve without turning the project into one large codebase.

The Trade-off

Separating the applications adds setup and coordination overhead, but it reflects a more realistic product structure and keeps guest-facing, server, and administrative concerns isolated.

The Result

The repository now provides a foundation for a full Airbnb-style platform with guest, host, and admin flows. The key walkthrough is the architectural decision to keep those concerns in separate applications: it makes ownership and deployment boundaries clear, even though it adds setup overhead. The guest frontend is deployed on Render; backend and admin deployment links will be added once those services are hosted and their environment variables are configured.
