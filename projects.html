Portfolio Website — Personal Site Architecture

Problem

I needed a single site to hold every project and case study I produce going forward — one that could grow term over term without a rebuild each time.

Approach

I split the site into independent pages (home, about, projects, contact) rather than one long scroll. Each project doubles as its own case study, opening in this slide-in panel so the grid stays a fast visual scan while the full write-up is one click away.

Trade-offs

I chose plain HTML/CSS over a framework or static site generator. That kept the build simple and dependency-free while I was still learning fundamentals, at the cost of manually duplicating markup (e.g. the header/footer on every page) instead of templating it.

Outcome & Next Step

The structure has held up across three terms of new content without needing a rewrite. The next improvement is reducing that markup duplication — likely by moving to a build tool or JS-rendered includes for shared header/footer.

Urban Threads — A Full Firebase E-Commerce App

Problem

Every project before this one either had no backend at all or leaned on localStorage. This assignment needed real accounts and a cart that actually persists — Firebase Authentication and Firestore, not hardcoded product data.

Approach

Products live in a Firestore products collection and load dynamically on the shop page. Each signed-in user's cart is stored under their own users/{uid}/cart subcollection rather than localStorage, so it follows them across devices instead of staying stuck in one browser.

Trade-offs

I let shoppers browse and search the whole catalog without an account, and only prompt for login at the moment they click "Add to Cart." That's more work than just gating the entire shop behind a login wall, but it matches how real stores behave — you don't need an account to window-shop.

Outcome & Next Step

Fully working store with category filtering, search, and pagination on top of the base requirement. Next step is an admin panel so I can manage the product catalog from a form instead of typing documents into the Firebase console by hand.

Google Keep Clone (React) — Rebuilding with Component State

Problem

I'd already built this as a vanilla JS clone. The React version had to prove I could actually structure an app with components and shared state instead of one long script — plus add one manual feature and one AI-assisted feature and be honest about which was which.

Approach

Every piece of state — notes, labels, theme, reminders — lives in one hook, useKeepStore, instead of scattered across components. Labels were the manual build; dark mode and drag-and-drop reordering were the AI-assisted features, where I used AI to help scaffold the logic and then verified every interaction by hand in the browser.

Trade-offs

Notes still persist to localStorage rather than a backend. That kept the assignment focused on component structure and state management rather than infrastructure, at the cost of notes not syncing between devices the way Urban Threads' cart does.

Outcome & Next Step

Masonry note grid, label filtering, archive/trash with a 7-day auto-purge, and reminders with due-date sorting all work. Next step is swapping localStorage for Firebase, the same pattern I already proved out on Urban Threads.

Book Library — Working With a Real API

Problem

Every project so far used data I controlled — hardcoded, Firestore, or localStorage. This one needed a real third-party API, which meant handling failures and slow responses instead of assuming the data is always just there.

Approach

Book data comes from the Open Library API via fetch, with explicit loading and error states rather than a blank screen while the request is in flight or on failure. Search is submit-triggered rather than live-as-you-type, to avoid firing a request on every keystroke.

Trade-offs

Submit-triggered search costs a bit of the instant feedback a live search gives you, but it keeps request volume sane against a free public API with no key or rate-limit budget behind it.

Outcome & Next Step

Deployed to GitHub Pages — including tracking down a blank-page bug that turned out to be a missing base: './' in vite.config.js. Next step is adding pagination to the search results, the same way I added it to Urban Threads' product grid.

Quiz Widget — Scoring Logic, Not Just Display

Problem

I wanted a small project focused purely on JavaScript logic — tracking a score and a question index correctly — rather than layout, which every earlier project had already covered.

Approach

Score and question index are tracked in JavaScript variables, not read back from the DOM, so the result is always computed rather than counted off whatever happens to be on screen. Answer buttons use event delegation on the container instead of a separate listener per button.

Trade-offs

Questions are hardcoded directly in the JS file rather than loaded from a separate JSON file or API. For a quiz this size that's the right call — pulling in a fetch layer for a dozen static questions would be complexity with no real payoff.

Outcome & Next Step

Instant feedback per question and a final score screen at the end. Next step is moving the question set into its own JSON file so I can add more questions without touching the scoring logic at all.

Twitter/X Clone — Interactivity and State in the Browser

Problem

Every project before this one was a static layout clone — good for CSS practice, but none of them needed to remember anything. I wanted a build that had to track state and respond to user actions in real time, closer to how a real product behaves.

Approach

I rebuilt the core Twitter/X feed interface with HTML and CSS for the layout, then used JavaScript to handle interactions — composing a post, updating counts, and reflecting state changes in the DOM immediately rather than reloading anything.

Trade-offs

I kept state in memory in the browser rather than wiring up a backend or persistence layer. That let me focus on getting the interaction logic and DOM updates right first, at the cost of nothing being saved between page reloads.

Outcome & Next Step

It's my most functionally complete project so far — real interactivity rather than a static clone. The next step is adding persistence, likely with local storage first and an API later, so state survives a refresh.

YouTube — Layout Precision at Scale

Problem

YouTube's layout looks simple until you try to rebuild it — a fixed sidebar, a sticky top bar, and a video grid that has to reflow cleanly at every screen size. I wanted a layout exercise that would actually expose sloppy CSS.

Approach

I built the sidebar, top search bar, and video grid as independent CSS Grid/Flexbox regions rather than one giant layout, so each piece could be reasoned about and fixed on its own. The thumbnail grid uses auto-fill with a minimum card width so it reflows on its own as the viewport shrinks, instead of hardcoded breakpoints for every screen size.

Trade-offs

The sidebar collapses to icons only below a certain width rather than hiding completely, which took more CSS than a simple "hide on mobile" rule — but it keeps navigation reachable instead of hidden behind a menu button, matching how the real site behaves.

Outcome & Next Step

A pixel-close, fully responsive recreation of the YouTube homepage layout. Next step would be wiring the thumbnails to a real API (like the YouTube Data API) instead of static placeholder content, the same shift Book Library already made.
