CASE STUDIES

How I built it, and what I'd change

Portfolio Website — Personal Site Architecture

Problem

I needed a single site to hold every project, certificate, and case study I produce going forward — one that could grow term over term without a rebuild each time.

Approach

I split the site into independent pages (home, about, projects, contact) rather than one long scroll, so each area can be extended without touching the others. Projects and certificates use a horizontally scrollable card layout so new entries can be appended rather than requiring a redesign.

Trade-offs

I chose plain HTML/CSS over a framework or static site generator. That kept the build simple and dependency-free while I was still learning fundamentals, at the cost of manually duplicating markup (e.g. the header/footer on every page) instead of templating it.

Outcome & Next Step

The structure has held up across three terms of new content without needing a rewrite. The next improvement is reducing that markup duplication — likely by moving to a build tool or JS-rendered includes for shared header/footer.

Tools Used: HTML, CSS, JavaScript, Git, GitHub, Chrome DevTools

Netflix Landing Page — Recreating a Production Layout

Problem

Static clones are useful for practice, but only if they force you to solve layout problems you can't shortcut. I picked Netflix's landing page because its hero section, feature grid, and FAQ accordion each needed a different layout technique.

Approach

I used CSS Grid for the feature section (fixed structure, predictable rows/columns) and Flexbox for the hero and footer (content that needs to grow/shrink with the viewport). Background images and overlay text were layered using absolute positioning inside a relatively positioned container.

Trade-offs

Matching the reference design pixel-for-pixel took longer than building something "close enough," but it forced me to understand why Grid and Flexbox each fit different parts of the layout, instead of defaulting to one for everything.

Outcome & Next Step

The layout holds up across breakpoints from mobile to desktop with no broken overlays. If I revisited it, I'd rebuild the FAQ section as an interactive accordion with JavaScript instead of a static list.

Tools Used: HTML, CSS, Git, GitHub, Chrome DevTools

Responsive Design — Consistent Layouts Across Breakpoints

Problem

Every project in this portfolio needs to work on a phone as well as a desktop. Rather than treat this per-project, I standardized an approach I now reuse across all of them.

Approach

I use relative units (%, rem) over fixed pixel widths wherever content needs to flex, media queries to restructure layout (e.g. stacking a horizontal nav into a vertical one) rather than just shrinking it, and test at specific breakpoints rather than only resizing the browser window casually.

Trade-offs

Designing mobile-first would have caught some of these issues earlier; I built desktop-first and retrofitted breakpoints, which meant more rework on spacing and alignment than if I'd flipped the order.

Outcome & Next Step

All projects in this portfolio are usable from ~320px up. On the next project, I'm switching to a mobile-first build order to avoid the retrofit cost.

Tools Used: HTML, CSS, Media Queries, Flexbox, Chrome DevTools

Version Control with Git — Workflow, Not Just Backup

Problem

Early on I was using Git purely as a backup tool — commit everything, push occasionally. That works until something breaks and there's no clear history to trace it back through, and it completely falls apart once more than one person is pushing to the same repo.

Approach

I moved to committing at logical checkpoints with descriptive messages, and on the iHub Africa capstone I managed a full feature-branch workflow for a 6-person team: branches per feature, pull requests before merge, and code review before approval.

Trade-offs

Enforcing PR review before merge slowed down how fast individual features landed, but it caught conflicting changes before they hit `main` instead of after — worth the trade-off once more than one person is touching the codebase.

Outcome & Next Step

The team shipped without a broken `main` branch at any point. Next, I want to get comfortable resolving merge conflicts from the command line instead of relying on a GUI tool.

Tools Used: Git, GitHub, Command Line, VS Code
